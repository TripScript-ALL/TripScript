# TripScript 앱 소개서

## 1. 프로젝트 개요

**TripScript**는 해외여행 중 발생한 영수증을 여행 단위로 모으고, 참여자별 사용량과 실제 정산 금액을 관리하는 해외결제 영수증 정산 플랫폼이다.

일반적인 더치페이 앱은 결제금액을 단순히 나누는 데 집중하지만, TripScript는 해외결제에서 실제 정산을 어렵게 만드는 요소까지 함께 다룬다.

- 여러 국가와 여러 통화를 거치는 여행 지출
- 카드 결제 시 국제브랜드 수수료와 국내 카드사 해외서비스 수수료
- 현지통화에서 USD, USD에서 KRW로 이어지는 환율 변환
- 현금 환전 시 사용자가 실제로 적용받은 환율
- 영수증 품목별 수량 배분과 참여자별 정산 대상 지정
- 여행 대표자와 참여자 간 권한 차이
- 영수증 이미지 기반 자동 인식

TripScript의 목표는 단순한 "n분의 1 계산기"가 아니라 **해외결제 환경을 반영한 여행 정산 플랫폼**이다.

## 2. 핵심 문제 정의

해외여행 정산은 국내 결제 정산보다 복잡하다. 같은 100유로 결제라도 실제 원화 부담액은 결제 방식, 카드사, 국제브랜드, 환율 기준일, 해외서비스 수수료에 따라 달라질 수 있다.

TripScript는 이 문제를 다음 방식으로 해결한다.

- 영수증 총액과 품목 합계를 비교해 입력 오류를 줄인다.
- 품목마다 참여자별 수량을 배분해 현실적인 정산 구조를 만든다.
- 카드 프로필을 사용자별로 분리해 본인 카드만 사용할 수 있게 한다.
- 카드사, 브랜드, 신용/체크 구분에 따른 대표 수수료 정책을 DB화한다.
- 카드 상품명 기반 LLM 리서치로 상품별 수수료 후보를 보강한다.
- 해외 특화 카드의 수수료 면제/우대 정책은 상품별 override 구조로 분리한다.
- 실제 카드 청구액을 사용자가 입력하면 추정액보다 우선 반영한다.
- 영수증 이미지는 Gemini 기반 인식으로 초안을 자동 생성한다.

## 3. 주요 사용자 흐름

1. 사용자는 카카오 로그인 또는 이름/전화번호 방식으로 로그인한다.
2. 카카오 로그인 사용자는 초기 설정에서 닉네임, 선택 전화번호, 정산 계좌, 결제 카드를 확인한다.
3. 사용자는 여행을 생성하고 여행 기간, 방문 국가, 대표 이미지를 설정한다.
4. 여행 생성자는 대표자가 되며, 초대 코드를 통해 다른 참여자를 초대할 수 있다.
5. 참여자는 초대 코드로 여행에 들어오고, 본인이 결제한 영수증을 등록할 수 있다.
6. 영수증 등록 시 이미지를 업로드하면 Gemini가 상호명, 날짜, 금액, 통화, 품목 초안을 인식한다.
7. 사용자는 결제자, 결제수단, 카드 또는 현금 정보를 확인하고 수정한다.
8. 품목별로 누가 몇 개를 부담했는지 입력한다.
9. 서버는 환율과 카드 수수료 정책을 바탕으로 정산에 반영할 원화 기준 금액을 계산한다.
10. 여행 상세 하단의 고정 총지출 바에서 원화 총액과 통화별 지출을 확인하고 바로 정산 화면으로 이동한다.
11. 정산 화면에서 원래 영수증별 부담 흐름과 최종 상계 결과를 토글해 확인한다.
12. 필요한 경우 내가 받을 정산을 카카오톡 공유 또는 문구 복사로 요청한다.

## 4. 구현된 주요 기능

### 4.1 회원, 카카오 로그인, 프로필

- 이름/전화번호 기반 회원가입과 로그인을 지원한다.
- 카카오 로그인으로 서비스 계정을 생성하고 서버 JWT를 발급한다.
- 앱을 종료했다가 다시 실행해도 로그인 상태가 유지되도록 로컬 세션을 저장한다.
- 카카오에서 사업자 인증 없이 이름/전화번호를 받을 수 없는 경우를 고려해 닉네임 기반 표시명 흐름을 사용한다.
- 닉네임을 변경하면 백엔드가 여행 대표자, 참여자, 영수증 결제자, 품목 배분 이름을 새 표시명으로 동기화한다.
- 닉네임 변경 직후 앱 캐시를 갱신해 여행 상세와 정산 화면에 새 표시명을 반영한다.
- 최초 로그인 후 초기 설정 화면에서 표시명, 선택 전화번호, 카드, 정산 계좌를 입력할 수 있다.
- 마이페이지에서 계정 요약, 참여 여행 수, 대표 여행 수를 확인할 수 있다.
- 마이페이지에서 정산금을 받을 은행, 계좌번호, 예금주를 관리한다.
- 회원탈퇴 시 사용자 계정, 개인 카드, 여행 참여 정보가 삭제된다. 사용자가 대표자인 여행은 함께 삭제된다.

### 4.2 여행 관리

- 여행 생성 시 대표자가 자동으로 지정된다.
- 여행 기간은 시작일과 종료일을 함께 관리한다.
- 여행 생성/수정 시 기간 선택 UI를 제공한다.
- 여행 생성/수정 시 방문 국가를 검색 가능한 선택 UI로 입력한다.
- 여행 상세 화면에서 여행 기간, 방문 국가, 참여자, 지출 추이, 영수증 목록을 통일된 섹션 스타일로 확인할 수 있다.
- 여행 상세 하단에는 총 지출과 정산하기 버튼을 고정해 영수증 목록이 길어도 정산 진입점을 놓치지 않게 했다.
- 대표자는 여행 정보, 기간, 커버 이미지, 참여자를 관리할 수 있다.
- 일반 참여자는 여행을 삭제하거나 핵심 정보를 수정할 수 없고, 본인이 여행에서 나갈 수 있다.
- 여행 목록과 여행 상세에는 방문 국가 국기, 원화 총액, 통화별 지출이 표시된다.
- 여행 목록은 일정 기준 정렬과 카드/리스트 보기 설정을 지원한다.

### 4.3 대표자와 참여자 권한

TripScript는 권한을 크게 두 그룹으로 나눈다.

| 권한 항목 | 대표자 | 참여자 |
| --- | --- | --- |
| 여행 정보 수정 | 가능 | 불가 |
| 여행 기간 수정 | 가능 | 불가 |
| 여행 커버 이미지 수정 | 가능 | 불가 |
| 참여자 추가/삭제 | 가능 | 불가 |
| 초대 코드 확인 | 가능 | 가능 |
| 여행 나가기 | 제한적 | 가능 |
| 영수증 등록 | 가능 | 가능 |
| 본인 결제 영수증의 결제 정보 수정 | 가능 | 가능 |
| 타인 결제 영수증의 결제 정보 수정 | 가능 | 불가 |
| 영수증 품목 및 분배 수정 | 가능 | 가능 |

대표자는 여행 전체를 관리하는 관리자이고, 참여자는 본인의 결제 건과 품목 분배에 참여하는 사용자로 정의한다. 백엔드는 닉네임 변경 이후에도 `name`, `nickname`, `displayName` 별칭을 모두 고려해 결제자 권한을 판단한다.

### 4.4 영수증 입력과 품목별 정산

- 영수증은 단순 총액 입력이 아니라 품목 중심으로 관리한다.
- 각 품목에는 품목명, 단가, 수량, 총액, 카테고리, 참여자별 수량 배분을 입력한다.
- 기본 정산 대상자는 자동 선택하지 않고, 사용자가 직접 선택하도록 한다.
- 품목별 수량 배분 방식은 단순 체크보다 현실적인 사용량 기반 정산에 적합하다.
- 영수증 총액과 품목 합계가 일치하는지 확인하고, 차이가 있으면 저장 전 사용자에게 알려준다.
- 품목 편집은 품목 선택 시 팝업으로 열리도록 구성했다.
- 여행 상세의 영수증 목록은 기본적으로 품목 5개까지만 보여주고, 필요할 때 확장해 긴 영수증도 부담 없이 볼 수 있다.
- 영수증 등록 화면에서는 영수증 이미지 선택 후 인식 결과와 인식 소요 시간을 확인할 수 있다.

### 4.5 영수증 이미지 인식

현재 영수증 인식은 백엔드에서 Gemini API를 호출하는 구조다.

```text
이미지 업로드
→ 백엔드 저장
→ CamScanner식 평면화/리사이즈
→ Gemini 2.5 Flash 인식
→ 앱 영수증 스키마 JSON 생성
→ 총액/품목 검증
→ 입력 화면에 반영
```

인식 안정성을 위해 다음 처리를 적용했다.

- 업로드 이미지는 백엔드에서 통제한다.
- Gemini API key는 앱이 아니라 서버에만 둔다.
- 같은 이미지, 같은 통화, 같은 모델 설정은 서버 메모리 캐시를 사용해 중복 호출을 줄인다.
- 429 쿼터 에러가 오면 `retry in Ns`를 읽어 짧게 한 번 자동 재시도한다.
- 그래도 실패하면 긴 원문 대신 사용자 친화 메시지를 보여준다.

### 4.6 통화와 환율

지원 통화는 한중일과 유럽 주요 여행 통화를 중심으로 정리했다.

```text
KRW, USD, EUR, JPY, CNY, GBP, CHF, SEK, NOK, DKK, ISK, PLN, CZK, HUF
```

- 여행 총액은 정산 기준을 위해 원화 합계를 중심으로 보여준다.
- 동시에 통화별 원금액 합계도 함께 보여 여행 중 어떤 통화를 얼마나 썼는지 확인할 수 있다.
- 환율은 백엔드에서 관리하며, 결제일 기준 환율을 우선 사용한다.
- 현재는 외부 환율 API 조회와 서버 fallback 값을 함께 사용하는 MVP 구조다.
- 실제 카드 청구는 카드사 접수/매입 시점 환율과 차이가 날 수 있으므로, 사용자가 실제 청구액을 입력하면 그 값을 우선 반영한다.

### 4.7 카드 프로필과 카드 상품 카탈로그

- 카드 정보는 사용자별로 분리되어 저장된다.
- 다른 계정에서 등록한 카드는 보이지 않도록 DB 기준으로 분리했다.
- 메인 화면의 사이드 메뉴에서 카드 목록 화면으로 들어갈 수 있다.
- 카드 등록 시 신용카드/체크카드 타입을 먼저 선택한다.
- 카드사 또는 은행은 드롭다운으로 선택하고, 카드 상품명은 사용자가 직접 입력한다.
- 입력된 카드 상품명을 바탕으로 백엔드가 수수료 리서치를 백그라운드로 수행한다.
- 국제브랜드와 카드 끝번호 4자리를 등록할 수 있다.
- 카드번호 전체, CVC, 유효기간은 저장하지 않는다.
- BC 계열 카드는 카드사/은행 선택과 BC 세부 발급사를 분리해 관리한다.
- 카드 목록에는 수수료 리서치 상태와 핵심 수수료율을 짧게 보여주고, 긴 LLM 설명은 과하게 노출하지 않는다.

카드 DB는 다음 단계 구조를 갖는다.

- 카드사 및 은행 단위 대표 수수료 정책
- 카드 상품명 카탈로그
- 해외 특화 카드의 수수료 면제/우대 override
- 카드명 기반 LLM 리서치 결과

카드 수수료 리서치는 Gemini가 아니라 서버컴의 로컬 Ollama `qwen2.5:3b` 모델을 사용한다. 검색 후보는 DuckDuckGo 결과를 기반으로 수집하고, LLM은 근거 snippet에서 수수료 JSON만 보수적으로 추출한다.

### 4.8 해외결제 예상 정산액 계산

카드 결제는 백엔드에서 다음 흐름으로 계산한다.

```text
현지통화 결제금액
→ 현지통화에서 USD 환산
→ 국제브랜드 수수료 반영
→ USD에서 KRW 환산
→ 국내 카드사 해외서비스 수수료 반영
→ 정산 반영 원화 금액
```

예상 정산액 화면에는 다음 정보를 줄 단위로 보여준다.

- 현지통화 금액
- 현지통화에서 USD로 바뀔 때의 환율
- USD에서 KRW로 바뀔 때의 환율
- 국제브랜드 수수료율
- 국내 카드사 수수료율 또는 고정 수수료
- 환율 기준 날짜와 API 또는 fallback 출처
- 실제 청구액 입력 여부

실제 카드앱에서 확인한 원화 청구액을 입력하면 서버는 예상 계산액보다 실제 청구액을 우선 반영한다.

### 4.9 현금 결제

현금 결제는 카드 수수료를 적용하지 않는다.

사용자가 환전 당시 실제로 적용받은 환율을 입력하면, 서버는 그 환율을 기준으로 정산 원화 금액을 계산한다. 현금은 카드처럼 접수일, 국제브랜드 수수료, 카드사 수수료가 없으므로 사용자 입력 환율이 가장 중요한 기준이 된다.

### 4.10 이미지 업로드

- 여행 대표 이미지와 영수증 이미지를 등록할 수 있다.
- 앱에서 선택한 이미지는 백엔드 서버에 업로드된다.
- 서버는 업로드된 파일을 저장하고, 앱은 서버에서 반환된 media URL을 사용한다.
- 앱 재설치나 다른 기기 로그인 상황에서도 서버에 저장된 이미지를 다시 불러올 수 있다.
- Android release 빌드에서도 네트워크 및 이미지 업로드가 가능하도록 권한을 설정했다.

### 4.11 정산 결과와 카카오톡 공유

- 정산 계산은 백엔드 API에서 처리한다.
- 품목별 수량 배분과 영수증별 원화 기준 금액을 바탕으로 참여자 간 정산 관계를 만든다.
- 참여자별 지출, 받을 금액/보낼 금액, 송금 관계를 표시한다.
- 정산 화면은 `원래 흐름`과 `최종 상계`를 분리한다.
- `원래 흐름`은 각 영수증의 결제자에게 원래 보내야 하는 금액을 그대로 보여준다.
- `최종 상계`는 서로 주고받을 금액을 상계해 최소 송금 관계만 보여준다.
- 보낼 돈, 받을 돈, 다른 참여자 사이 정산을 탭으로 나눠 현재 로그인 사용자 기준으로 해석하기 쉽게 했다.
- 내가 받아야 하는 정산에서만 개별 카카오톡 공유와 문구 복사를 제공한다.
- 여행 전체 정산 요약도 참여자별 요약 아래에서 카카오톡 공유 또는 문구 복사할 수 있다.

### 4.12 앱 화면과 설정

- 메인 화면은 비행기 아이콘과 TripScript 브랜드를 사용한다.
- 사이드 메뉴는 여행목록, 마이페이지, 카드목록, 서비스 설명, 설정, 로그아웃으로 구성된다.
- 서비스 설명 화면은 해외결제 정산 흐름과 개인정보/외부 AI 사용 안내를 앱 안에서 확인할 수 있게 한다.
- 설정 화면에서는 시스템 테마, 라이트 테마, 다크 테마를 선택할 수 있다.
- 주요 입력 화면은 시스템 라이트/다크 테마에 맞춰 대비가 깨지지 않도록 정리했다.

## 5. 기술 구조

### 5.1 프론트엔드

- Flutter 기반 모바일 앱
- Android APK 빌드 지원
- Windows 로컬 환경에서 프론트 개발
- `API_BASE_URL` 빌드 인자를 통해 백엔드 주소 주입
- `KAKAO_NATIVE_APP_KEY` 빌드 인자를 통해 카카오 SDK 초기화
- Android 네이티브 MethodChannel 기반 카메라/갤러리 연동
- Provider 기반 상태 관리
- 릴리즈 빌드에서 백엔드 통신, 카카오 로그인, 이미지 업로드 지원
- 시스템 테마와 사용자 설정 테마 지원
- 카카오톡 공유 SDK 연동

### 5.2 백엔드

- FastAPI 기반 REST API 서버
- Docker Compose 기반 실행
- SQLite 기반 로컬 영속 DB
- 서버컴 배포 및 ngrok 터널 운영
- 이미지 업로드와 정적 미디어 제공
- Gemini 기반 영수증 이미지 인식
- Ollama 기반 카드 수수료 리서치
- 카드 수수료, 환율, 정산 계산을 서버에서 처리
- 관리자 페이지 컨테이너 분리
- 정산 API에서 원래 흐름 `grossTransfers`와 최종 상계 `transfers`를 함께 반환

### 5.3 배포 및 테스트 구조

- 프론트 개발은 노트북 Windows 환경에서 진행한다.
- 백엔드 개발 및 실행은 WSL/서버컴 Docker 환경에서 진행한다.
- 외부 모바일 기기 테스트는 ngrok 터널을 통해 서버컴 FastAPI 서버에 접근한다.
- 프론트 APK는 ngrok API 주소를 바라보도록 빌드한다.
- 관리 사이트는 별도 컨테이너로 분리해 앱 API 컨테이너와 독립적으로 운영한다.

## 6. 백엔드 DB 구조 요약

현재 백엔드는 SQLite DB를 사용한다. 주요 테이블은 다음과 같다.

| 테이블 | 역할 |
| --- | --- |
| `users` | 사용자 계정, 카카오 id, 닉네임 |
| `trips` | 여행 기본 정보와 대표자 user id |
| `trip_participants` | 여행 참여자 목록과 user id 매핑 |
| `user_trips` | 사용자별 여행 목록 매핑 |
| `receipts` | 영수증 결제 정보와 서버 계산 금액 |
| `receipt_items` | 영수증 품목 |
| `receipt_item_splits` | 품목별 참여자 수량 배분 |
| `card_profiles` | 사용자별 카드 프로필과 수수료 리서치 결과 |
| `card_fee_catalog` | 카드사/브랜드 대표 수수료 카탈로그 |
| `card_issuer_fee_policies` | 카드사, 브랜드, 신용/체크별 수수료 정책 |
| `card_products` | 카드 상품명 카탈로그 |
| `card_product_fee_overrides` | 트래블카드 등 상품별 예외 정책 |
| `exchange_rates` | 날짜별 환율 캐시 |
| `media_files` | 업로드 이미지 메타데이터 |

정산 결과는 별도 테이블로 저장하지 않고, 영수증/품목/분배/참여자 데이터를 기준으로 API 요청 시 계산한다. API는 원래 결제자에게 보내야 하는 흐름과 최종 상계된 송금 관계를 함께 반환한다.

## 7. 개인정보 및 외부 AI 사용 대응

TripScript는 영수증 인식 정확도와 속도를 위해 클라우드 LLM인 Gemini를 사용한다. 개인정보 지적에 대해서는 다음 원칙으로 대응한다.

- 클라우드 LLM 호출은 프론트가 아니라 백엔드에서 통제한다.
- Gemini API key는 앱에 포함하지 않는다.
- 영수증 이미지에서 정산에 필요한 필드만 구조화해 저장한다.
- 카드번호 전체, CVC, 유효기간은 수집하지 않는다.
- 카드 끝 4자리는 식별 편의용으로만 선택 저장한다.
- 같은 이미지는 캐시하여 반복 전송을 줄인다.
- 향후 운영 단계에서는 사용자 동의, 이미지 보관기간, 전송 전 민감정보 마스킹, 로컬 인식 fallback을 적용할 수 있다.

발표 시 핵심 문장은 다음과 같다.

> 클라우드 LLM은 정확도 검증을 위해 선택했지만, 개인정보 보호를 위해 백엔드 통제, 최소 저장, 카드번호 미수집, 사용자 동의, 로컬 대체 파이프라인을 전제로 설계했습니다.

## 8. 현재 한계와 향후 확장 계획

### 8.1 Gemini 무료 쿼터

현재 영수증 인식은 Gemini 무료 티어 쿼터 영향을 받는다. 이를 완화하기 위해 중복 이미지 캐시와 429 자동 재시도를 적용했다. 실제 시연이나 운영 단계에서는 Google Cloud Billing 연결 또는 유료 티어 전환을 고려한다.

### 8.2 환율 정확도 개선

현재 MVP는 결제일 기준 환율을 중심으로 계산한다. 실제 카드 청구는 결제일이 아니라 국제브랜드 또는 카드사 접수/매입 시점 환율이 적용될 수 있다.

향후에는 다음 값을 추가로 다룰 수 있다.

- 승인일
- 매입일
- 카드사 접수일
- 카드앱에서 확인한 거래미화금액
- 카드앱에서 확인한 실제 원화 청구액

### 8.3 카드 상품 DB 고도화

현재는 대표 카드사 수수료와 주요 상품 카탈로그를 seed 데이터로 사용한다. 향후에는 카드사 공식 상품설명서와 약관을 기반으로 다음 데이터를 확장할 예정이다.

- 전 카드사 상품명
- 발급 가능 여부
- 신용/체크 구분
- 국제브랜드별 선택 가능 여부
- 해외서비스 수수료
- 국제브랜드 수수료
- 수수료 면제, 캐시백, 외화머니 결제 예외

### 8.4 구조 고도화

- `receipts.payer_user_id` 추가
- `receipt_item_splits`를 이름 기반에서 user id 기반으로 전환
- 관리자 페이지에서 카드 상품/수수료 직접 관리
- 이미지 원본 자동 삭제 정책
- 영수증 인식 결과 품질/시간 통계 대시보드
